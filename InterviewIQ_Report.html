1 Executive Summary & Introduction

InterviewIQ is a comprehensive, web-based application engineered to process user-uploaded resumes and job descriptions, generating tailored interview questions and conducting voice-based mock interviews with real-time performance analytics and a personalized coaching assistant.

The recruitment landscape has increasingly shifted toward automated screening, yet the preparation phase for candidates remains largely manual and unstructured. InterviewIQ addresses this by providing a closed-loop preparation environment. The system extracts text from uploaded PDF resumes, compares them against target job descriptions using a large language model (Gemini), and produces a structured gap analysis. It then generates non-repeating interview questions across multiple categories and difficulty levels.

The core functionality is a live, voice-enabled mock interview conducted over WebSockets. The system speaks the questions, transcribes the user's spoken answers, evaluates the content and delivery in real-time, adapts the subsequent questions based on performance, and generates a final performance summary. A supplementary chat assistant allows users to query their own data for further preparation. This report details the architectural decisions, algorithmic implementations, and engineering constraints managed during the development of the system over the 30-day challenge period, covering all 30+ source files in the repository.

2 Problem Statement & Motivation

Current interview preparation tools exhibit several functional limitations that reduce their effectiveness for job seekers. These limitations can be categorized into three primary areas:

  1. Lack of Contextual Relevance: Standard question banks provide generic queries. They do not analyze the specific intersection of a candidate's resume and the target job description. This leads to preparation that misses critical skill gaps and fails to address the specific requirements of the role being applied for.
  2. Absence of Vocal Practice: Most platforms rely on text input or multiple-choice selections. Real interviews require verbal articulation under time pressure. Text-based tools do not measure speaking fluency, pacing, filler word usage, or the ability to structure a spoken response coherently.
  3. Subjective Feedback Mechanisms: Candidates rarely receive objective, immediate feedback on both the technical content of their answers and the quality of their delivery without hiring expensive human coaches. Existing automated tools often provide binary correct/incorrect feedback, which is insufficient for behavioral or situational questions.

InterviewIQ addresses these issues by combining document analysis, adaptive question generation, real-time voice processing, and personalized coaching into a single, self-hostable backend system. The motivation for this project stems from the need to democratize access to high-quality, personalized interview coaching.

Engineering Constraints Addressed

  • AI API costs and latency require strict deduplication of identical inputs to prevent redundant processing.
  • Concurrent user actions (e.g., double-clicking submit) must not create duplicate database records or trigger race conditions.
  • User-uploaded documents must be treated as untrusted data to prevent prompt injection attacks against the LLM.
  • Voice processing must not introduce latency that disrupts the real-time interview flow, necessitating asynchronous background processing for complex metrics.

3 System Architecture & Technology Stack

The application follows a modular monolith architecture built on FastAPI. The HTTP routing and middleware are centralized in main.py, while domain logic is separated into distinct service modules. The frontend is a lightweight vanilla JavaScript client served as static files from the static/ directory, minimizing build complexity and deployment overhead.

4 Document Processing & AI Analysis Engine

The core document processing logic is encapsulated in services.py and helpers.py. This module handles the ingestion of PDF resumes, text extraction, version control, and the initial AI-driven gap analysis.

4.1 PDF Extraction & Validation

When a user uploads a resume, the system uses PyMuPDF to extract text in memory. The extract_resume_text function enforces strict validation: files must be valid PDFs, cannot be password-protected, and must yield between 50 and 30,000 characters of readable text. This prevents the system from processing scanned images or corrupted files, returning specific HTTP 422 errors with user-friendly messages.

4.2 Idempotent Versioning System

To prevent redundant AI API calls, the system implements a content-hash-based versioning system. Every resume and job description is hashed using SHA-256. Before creating a new database record, the system queries for the latest version. If the hash matches, the existing record is reused. If it differs, a new version is created.

To handle race conditions where two identical requests arrive simultaneously, the system uses a retry loop with a maximum of three attempts, relying on PostgreSQL unique constraints to reject the duplicate. This ensures idempotency without requiring complex distributed locks.

for _ in range(MAX_VERSION_RETRIES):
    latest = get_latest_resume(db, user_id)
    if latest and latest.resume_hash == resume_hash: return latest
    resume = Resume(version_no=(latest.version_no+1 if latest else 1), ...)
    db.add(resume)
    try: db.commit()
    except IntegrityError: db.rollback(); continue

4.3 AI Gap Analysis & Model Fallback

The analysis module constructs a prompt containing the resume and job description, enclosed in random UUID marker fences to establish a trust boundary. The system requests a structured JSON response. To ensure reliability, the system iterates through a list of three Gemini models in services.py. If a model fails due to network issues, rate limits, or returns invalid JSON that fails Pydantic validation, the system catches the exception and attempts the next model. Only if all models fail does the endpoint return an HTTP 503 status.

MODELS = ["models/gemini-flash-lite-latest",

raise AnalysisUnavailableError(f"All AI models failed: {last}")

5 Adaptive Question Generation System

The question generation logic is implemented in question_service.py. This module is responsible for creating tailored interview questions while strictly enforcing a zero-duplication policy.

5.1 Prompt Construction

The build_prompt function assembles the context for the LLM. It includes the current resume, job description, and the structured analysis notes (missing requirements, strengths). Crucially, it includes a list of up to 150 previously generated questions, explicitly instructing the model not to rephrase them. The prompt enforces a strict JSON output schema containing the question text, category, difficulty, target skill, and ideal answer points.

5.2 Three-Layer Deduplication Algorithm

Preventing question repetition is handled at three distinct layers to ensure high quality:

  1. Prompt Layer: The LLM is provided with the text of previously generated questions and explicitly instructed not to rephrase them.
  2. Application Layer: The system normalizes the generated questions by removing stop words and applying a basic stemming algorithm. It calculates the Jaccard similarity between the content words of the new question and existing questions. The formula used is:
    Similarity(A, B) = |A ∩ B| / |A ∪ B|. If the similarity exceeds 0.6, the question is discarded as a near-duplicate.
  3. Database Layer: The questions table enforces a unique constraint on (user_id, question_hash). The insertion query uses ON CONFLICT DO NOTHING to silently ignore exact duplicates that bypass the application layer.

5.3 Concurrency Control

Question generation is serialized per user using PostgreSQL transaction advisory locks. The lock_question_generation function acquires a lock based on the user's ID, ensuring that concurrent requests from the same user do not result in duplicate batch numbers or redundant AI calls.

6 Voice Mock Interview Engine

The mock interview engine is the most complex component of the system, distributed across interview_service.py, interview_summary_service.py, and adaptive_interviewer.py. It manages the lifecycle of a voice-based interview session.

6.1 Session Lifecycle Management

In interview_service.py, the create_session function initializes an interview by snapshotting the current resume and job description versions. This ensures that even if the user updates their documents later, the interview remains consistent. The system enforces a strict state machine: sessions transition from preparing to active upon starting, and to completed, interrupted, or failed upon termination. A partial unique index in the database ensures a user can only have one active or preparing interview at a time.

6.2 WebSocket Communication Flow

The live interview is conducted via the WebSocket endpoint /interviews/{id}/voice defined in main.py. The client uses the browser's SpeechSynthesis API to read the question text and the SpeechRecognition API to capture the user's answer. The transcript is sent to the server as a JSON payload:

// Client-side WebSocket message
socket.send(JSON.stringify({
  type: "answer_transcript",
  text: event.results[0][0].transcript
}));

Upon receiving the transcript, the server records the turn, calculates deterministic voice metrics, and invokes the adaptive interviewer to generate the next question. The connection terminates automatically when the configured session duration expires.

6.3 Adaptive Interviewer Logic

The adaptive_interviewer.py module is responsible for evaluating the user's answer and selecting the next question. After each answer, the system sends the resume, job description, interview history, and the current transcript to the LLM. The model is instructed to return a validated JSON object containing:

  • score (0-100): An evaluation of the answer's quality.
  • feedback: Specific, concise feedback for the user.
  • strengths and gaps: Arrays identifying key points.
  • next_question: An object containing the category, difficulty, target skill, and text for the subsequent question.

The system uses this output to adjust the difficulty and category of the subsequent question, ensuring the interview adapts to the candidate's demonstrated proficiency. If the AI model fails during the interview, the system falls back to the next saved question from the question bank, ensuring the interview continues without interruption.

6.4 Interview Summarization

Upon completion, interview_summary_service.py aggregates the data from all turns. It calculates an overall score, identifies strong and weak areas, lists skills to learn, and generates a comprehensive text summary. This summary is persisted in the interview_summaries table and made available via the /interviews/{id}/summary endpoint.

7 Voice Analysis & Pronunciation Pipeline

The voice analysis system is split into two parts: deterministic metrics calculated in real-time, and asynchronous pronunciation scoring handled by a background worker. The relevant files are voice_analysis_service.py, audio_analysis_queue.py, speech_service.py, and pronunciation_worker.py.

7.1 Deterministic Delivery Metrics

To avoid the latency and cost of using an LLM for basic speech analysis, the system calculates delivery metrics using deterministic algorithms in voice_analysis_service.py. The analyze_transcript function processes the text and timing data to compute:

  • Speaking Rate (WPM): Calculated by dividing the word count by the duration in minutes. WPM = Total Words / (Duration_ms / 60000).
  • Fluency Score: Derived by subtracting penalties for filler words and long pauses from a base score of 100. Fluency = 100 - (5 * fillers) - (6 * long_pauses) - (2 * pauses).
  • Clarity Score: Calculated by penalizing repeated words and filler usage. Clarity = 100 - (3 * repeated) - (2 * fillers).
  • Grammar Score: Assigned based on total word count, with a bonus applied if the transcript ends with standard punctuation (. ! ?).
  • Pace Score: Evaluated against ideal speaking ranges. 95 if 120-180 WPM, 80 if 100-210 WPM, else 60.

These metrics are stored in the voice_analyses table and returned to the client immediately after each turn.

7.2 Asynchronous Pronunciation Scoring

Browser-based speech recognition does not expose phoneme data, making accurate pronunciation scoring impossible in the main request loop. To solve this, the system implements an asynchronous pipeline:

  1. Audio Capture: During the interview, the client records short audio chunks using the MediaRecorder API and sends them to the server.
  2. Queueing: The audio_analysis_queue.py module pushes these audio chunks to a Redis queue named interviewiq:pronunciation. The main interview loop does not wait for this processing.
  3. Background Processing: The pronunciation_worker.py script runs as a separate process, consuming items from the Redis queue. It uses the facebook/wav2vec2-lv-60-espeak-cv-ft model to compare the transcript phonemes with the phonemes detected from the audio.
  4. Result Update: Once processed, the worker updates the pronunciation_score and analysis_status fields in the voice_analyses table. Temporary audio files are deleted after processing or after a retention period defined by AUDIO_RETENTION_SECONDS.

8 Personalized Coaching Assistant

The personalized coaching assistant is implemented in assistant_service.py and exposed via the /assistant/messages endpoints. It allows users to ask follow-up questions grounded in their specific data.

8.1 Context Assembly

When a user sends a message, the assistant does not rely solely on the LLM's general knowledge. Instead, it constructs a highly specific context window. The system retrieves the user's latest resume, job description, gap analysis, generated questions, and interview history. This data is formatted and injected into the system prompt.

8.2 Prompt Engineering & Grounding

The prompt explicitly instructs the LLM to act as a career coach and to base its answers exclusively on the provided context. If the user asks a question that cannot be answered using their data, the model is instructed to state that it does not have the information, rather than hallucinating. This ensures the assistant remains a reliable tool for interview preparation.

8.3 Message Persistence

All conversation messages are stored in the assistant_messages table, linked to the user's ID. This allows the user to review past interactions. Furthermore, these messages are included in the account export functionality and are permanently deleted when the user invokes the account deletion endpoint, ensuring complete data sovereignty.

9 Authentication, Security & Account Management

Security is managed across auth.py, services_auth.py, account_service.py, and email_service.py. The system implements a robust, stateful authentication mechanism.

9.1 Password Storage & Session Management

Passwords are hashed using Argon2id, a memory-hard function resistant to GPU-based cracking. Upon successful login, the system issues a JWT stored in an HttpOnly cookie. To prevent session hijacking, the system maintains a blacklist of revoked tokens in Redis. When a user logs out, the token's JTI (JWT ID) is added to Redis, and the middleware checks this blacklist on every subsequent request, ensuring immediate session termination.

9.2 Email Verification & Password Recovery

The email_service.py module handles asynchronous email delivery via SMTP. It supports email verification flows and password recovery. The password reset flow uses time-limited, hashed tokens. Crucially, the API responses for password reset requests do not reveal whether an email address exists in the database, preventing user enumeration attacks.

9.3 Data Sovereignty

The account_service.py module provides two critical endpoints: /account/export and /account (DELETE). The export endpoint aggregates all user data (resumes, analyses, questions, interview history, and assistant messages) into a structured JSON format, excluding sensitive credentials. The deletion endpoint performs a cascading delete of all associated records, ensuring complete and irreversible data removal.

10 Database Schema & Data Modeling

The database schema is defined in models.py and db_structure.sql. It consists of eleven tables, all utilizing UUID primary keys to prevent enumeration attacks and facilitate distributed scaling.

10.1 Core Tables & Constraints

TablePurpose & Key Constraints
usersStores credentials and verification tokens. Enforces unique email and NOT NULL on password hash.
resumes / job_descriptionsStores versioned documents. Enforces unique (user_id, version_no) to prevent duplication.
resume_analysisStores LLM output. Enforces unique (user_id, analysis_hash) to ensure identical inputs yield a single record.

interview_sessionsTracks interview state. Includes a partial unique index WHERE status IN ('preparing','active') to enforce one active interview per user.

assistant_messagesStores chat history. Enforces role CHECK constraint (user, assistant).

10.2 Indexing Strategy

To optimize query performance, specific indexes were implemented:

  • Composite Indexes: Used on (user_id, created_at) for chronological retrieval of sessions and messages.
  • Partial Indexes: The partial unique index on interview_sessions ensures that a user cannot have multiple active interviews simultaneously, enforced at the database level rather than the application level.
  • JSONB Support: Columns storing AI outputs (e.g., others in resume_analysis, ideal_answer_points in questions) use the JSONB data type, allowing for flexible schema evolution without requiring immediate database migrations.

11.2 Middleware & Error Handling

The main.py file implements critical middleware. The add_request_id middleware injects a unique X-Request-ID header into every response, facilitating log correlation. The reject_oversized_requests middleware checks the Content-Length header before reading the body, returning an HTTP 413 error for uploads exceeding 5 MB. Error handling is centralized, returning specific HTTP status codes: 400 for missing inputs, 401 for auth failures, 422 for validation errors, and 503 for AI service unavailability.

12 Testing, CI/CD & Quality Assurance

A comprehensive testing strategy was implemented to ensure system reliability without incurring AI API costs during development. The test suite is located in test_fixes.py and test_questions.py, with fixtures defined in conftest.py.

  • Mock AI Client: The tests utilize a fake Gemini client. This allows the testing of prompt construction, output parsing, and database interactions without making actual API calls, ensuring the test suite runs quickly and at zero cost.
  • Database Isolation: Tests run against a dedicated database (suffix _test) and truncate only the tables relevant to the specific test case, ensuring test isolation and repeatability.
  • Continuous Integration: GitHub Actions workflows (defined in .github/workflows) execute the test suite against live PostgreSQL and Redis services on every push and pull request. This ensures that database schema changes or dependency updates do not break existing functionality.
  • Logging & Observability: Every request generates a structured log entry containing a unique Request ID, HTTP method, path, status code, and duration. Request bodies are never logged. This facilitates debugging in production without compromising user privacy.

13.2 Execution

The run_interview.sh script orchestrates the startup of the API server and the pronunciation worker simultaneously. It ensures that Redis is running before initiating the services. For production deployments, it is recommended to use a process manager like systemd or a container orchestration platform to manage the API and worker processes independently.

14 Conclusion

InterviewIQ provides a comprehensive, self-hostable solution for automated interview preparation. By combining document analysis, adaptive question generation, real-time voice processing, and personalized coaching, the system addresses the primary limitations of existing text-based preparation tools.

The development process focused on engineering rigor, implementing idempotent operations to control costs, database-level concurrency controls to ensure data integrity, and strict trust boundaries to secure AI interactions. The resulting application provides candidates with a measurable, adaptive, and realistic interview practice environment.

Through the 30-Day Innovation Challenge, the ML Quad team successfully delivered a production-shaped backend that demonstrates the practical application of large language models in a structured, stateful, and secure environment. The project serves as a foundation for future enhancements in automated recruitment and personalized education technologies.
